# 立体四目並べ最終盤の探索不要厳密判定と実装計画

## ――残余完成集合と三値決定図による58手目以降の任意局面評価――

作成日：2026年9月13日  
対象：4×4×4の重力付き立体四目並べ  
文書の性格：既存研究の定義・証明・実測結果の再構成、および将来の組込み計画  
作業範囲：本論文の作成のみ。既存の対戦コード、研究用コード、生成済み判定表は変更しない。

## 要旨

本論文は、立体四目並べの58手目以降について、現在盤面から得られる情報だけで最善対戦の勝ち・負け・引き分けを判定する方法を述べる。前提は、合法な未終局局面であり、双方とも直ちに勝てる着手がないことである。この前提以外に盤面の配置に関する適用条件を設けない。

方法の中心は、各色が四目を完成するために今後取得する必要のある空きマスの集合を、現在盤面から抽出することである。以後の勝敗を表す関数を事前に三値決定図へ変換しておき、評価時には現在盤面に関する真偽質問に答えるだけで結論を得る。三値決定図とは、真偽質問を順に分岐し、勝ち・引き分け・負けのいずれかを終端で返す表現である。評価時に未来の盤面を作成する処理は含まれない。

生成済みの表は、残り7マス以下の全242,709空き形状に対応する。表を選ぶ処理と特徴抽出を除けば、判定は最大32回の質問で終わる。前半では、使用する記号と用語、情報の十分性、判定の正しさ、残り3マス以下の直接式、既存リーチだけでは不足する反例、検証結果を記す。後半では、現在の評価処理を正しく整理し、`turn >= 58` の評価関数、呼出し順序、評価値の尺度、判定表の管理、置換表との整合、検証手順を具体化する。

**現行コードについての訂正。** 一部の評価関数にある `turn >= 60` の `return 0` は、最終盤の評価全体を引き分けにする処理ではない。別の関数 `reach_layer_intersection_t()` が最終盤の勝敗・引き分け判定を担当し、その戻り値が合成評価に加算される。前の研究報告では、この呼出し関係の説明が不足していた。本論文はこの訂正を前提とする。詳細な関数の定義と経路は第II部第8節に示す。

### 2.3 空きマス番号とビット表現

**空き形状**とはU、すなわちどのマスが空いているかだけの情報であり、既存の石の色は含まない。σだけでは柱の水平位置が失われるので、物理的な空き形状とσは区別する。

空きマスに、柱ごとに下から上へ、全体で0からE−1までの番号を付ける。柱間の並びは、空き高さと水平位置から一定の方法で決める。

| 記号 | 定義 |
|---|---|
| `I` | 空きマス番号全体の集合 `{0,…,E−1}`。E=0なら空集合。 |
| `i` | Iに属する空きマス番号。 |
| `u_i` | 空き番号iに対応する物理マス。 |
| `ν(T)` | 物理マス集合Tのうち空いているものを番号へ変換した集合。`ν(T)={i∈I : u_i∈T}`。 |
| `D_i` | `u_i` と同じ柱にあり、それより低い初期空きマスの番号集合。着手の前提となる番号を表す。 |
| `S` | Iの部分集合。主に、完成に必要な空きマス番号の集合を表す。 |
| `s(S)` | Sを整数で表したもの。`s(S)=Σ(i∈S) 2^i`。 |
| `bit(T)` | 物理マス集合Tの64ビット表現。座標 `(x,y,z)` のマスに `2^(x+4y+16z)` を割り当てて足し合わせる。 |

**ビット**は0または1を取る桁、**ビット盤面**は各物理マスを1ビットに対応させた整数、**マスク**は集合をビットで表した値をいう。64ビット盤面 `bit(T)` と、空き番号に対する小さなマスク `s(S)` を混同しない。

表の削減に使う**対称変換**とは、水平面の0・90・180・270度回転と、それらに鏡映を組み合わせた8通りの変換である。高さは変えず、重力と76ラインを保つ。**正規化**とは、対称な形状から一つの代表を決め、番号付けを統一する処理である。生成器では、変換後の空きビット盤面が最小になる変換を選び、その上で柱を空き高さ・水平位置の順に並べる。同値の変換が複数なら生成器に固定した順で最初のものを選ぶ。

### 2.4 適用前提

本論文の前提を**静穏条件C**と呼び、次で定める。

```text
C ⇔ Pが合法な未終局局面であり、
     H ∩ R_M = ∅ かつ H ∩ R_O = ∅
```

静穏とは、ここでは「双方の即置可能リーチがない」という限定された意味である。埋没リーチがないことや、今後リーチが作れないことまでは要求しない。

「58手目以降の任意局面」とは、**Cを満たす、58≤turn≤64のすべての局面**を意味する。満杯で既に勝者もない場合は別に引き分けとする。Cを満たさない局面へ静穏用の表を直接適用することは、定理の保証範囲外である。

## 3. 残余完成集合による盤面情報の保存

### 定義1　残余完成集合と入力ビット

色Xについて、初期に相手石を含まないラインを考える。そのライン上の初期空きマス番号の集合を、Xの**残余完成集合**と呼ぶ。「残余」は完成までに残っている部分という意味である。

**集合族**とは集合を要素に持つ集まりである。Xの残余完成集合族を `ℋ_X`、その存在を表す入力ビットを `q_X(S)` とする。

```text
ℋ_X = { ν(ℓ∩U) : ℓ∈ℒ かつ ℓ∩C_opp(X)=∅ }
q_X(S) = 1 ⇔ S∈ℋ_X
```

Pは未終局なので、ℋ_Xに空集合は含まれない。同じ残余集合を持つラインが複数あっても、ℋ_Xでは一つにまとめる。実装では各ラインの寄与をORでまとめる。

| Sの大きさ | `q_X(S)=1` の意味 |
|---:|---|
| 1 | Sの唯一のマスが、Xの既存リーチである。 |
| 2 | Sの2マスをともにXが取れば、そのラインが完成する。 |
| 3 | Sの3マスをすべてXが取れば完成する。 |
| 4 | 初期に全空きのラインであり、その4マスをXが取れば完成する。 |

例えばSが2マスの場合、現在はリーチでなくても、Xが一方を取るともう一方が新しいリーチになる。この情報を保存することが、既存リーチだけの規則との違いである。

### 定義2　完成条件と着手の合法性

`A_M` と `A_O` を、それぞれP以後にMとOが取得した空き番号の集合とする。両者は重ならない。`Z=A_M∪A_O` を取得済み番号の集合とする。これらは**証明と事前計算用の記号**であり、実行時に未来のA_M、A_Oを作ることを要求しない。

Xの完成条件 `F_X(A_X)` と、Zまで埋まったときに合法な空き番号の集合 `L(Z)` を定義する。

```text
F_X(A_X) = OR(q_X(S) : S⊆A_X)
L(Z) = { i∈I : i∉Z かつ D_i⊆Z }
```

`F_X=1` は、Xが四目を完成していることを表す。`D_i⊆Z` は、マスiの下にあった空きマスがすべて埋まったことを表す。

### 定理1　保存した情報の十分性

柱内の空き順序と全入力 `q_X(S)` が同じ二つの初期局面は、最善対戦の勝敗が同じである。

**証明。** 初期に相手石を含むラインは、石が取り除かれないのでXの四目にはならない。相手石を含まないラインは、初期に空いていた部分をすべてXが取得したとき、かつそのときだけXの四目になる。従って勝利の条件はF_Xに一致する。合法手の条件は重力による柱内順序だけであり、L(Z)に一致する。空き番号が同じ着手を対応付けると、合法手、途中の勝利、満杯引き分けがすべて保存される。そのため選択できる戦略と最善対戦の結果も保存される。証明終。

共有するマスには同じ空き番号を使うので、ラインの交差による競合は失われない。新しいリーチ、二重リーチ、埋没リーチの開放も、この対応に含まれる。

### 補題1　不要な入力の除去

Mの集合について大きさが `ceil(E/2)` を超えるもの、Oの集合について大きさが `floor(E/2)` を超えるものは省略できる。また、初期即置可能マスの単独集合は、Cの下で両色とも0である。

**証明。** 満杯まで指しても、MとOの着手回数はそれぞれ高々 `ceil(E/2)` と `floor(E/2)` である。それより大きな集合の全要素を同じ側が取ることはできない。単独集合についてはCの定義そのものである。証明終。

E≤6では両者が取れるのは高々3マスなので、大きさ4の完成集合は不要である。E=7ではMが4回指せるため、Mの大きさ4の完成集合も保存する。

## 4. 勝敗関数の事前コンパイル

### 4.1 決定図に関する定義

| 用語・記号 | 定義 |
|---|---|
| 真偽関数 | 複数の真偽入力から真または偽を返す関数。 |
| 三値関数 | 本論文では、真偽入力から `−1,0,+1` のいずれかを返す関数。 |
| BDD | Binary Decision Diagramの略。真偽関数を、入力に対する質問の分岐で表す二分決定図。 |
| MTBDD | Multi-Terminal Binary Decision Diagramの略。終端で複数種類の値を返せる決定図。本論文では三つの勝敗値を返す。 |
| 節点 | 決定図の一つの質問、または結果を置く場所。ゲーム木の局面節点とは別物である。 |
| 非終端節点 | 真偽質問を持ち、0用と1用の二つの行先を持つ節点。 |
| 終端節点 | 質問を持たず、勝敗値を返す節点。 |
| 根 | 決定図で最初に読む節点。「探索の根」と記した場合は、ゲーム木の探索を開始する局面を指す。 |
| 経路 | 根から質問の答えに従って終端まで進む節点列。 |
| `q` | ある空き形状に必要な入力ビット `q_X(S)` 全体を一つにまとめた呼び名。 |
| `var` | 決定図内で質問する入力変数の番号。勝敗を表す `v(P)` とは別の量である。 |
| `low,high` | ある非終端節点から、入力0のとき、入力1のときに進む行先。 |
| `(var,low,high)` | 一つの非終端節点の定義。 |
| 変数順序 | どの入力を先に質問するかの共通順序。各経路ではこの順番に従う。 |
| 節点共有 | 同じ入力番号と同じ二つの行先を持つ節点を一つにまとめること。 |
| 縮約 | 同じ質問を共有し、両行先が同じ質問を除去すること。関数の値を変えずに表現を小さくする。 |

決定図には循環がなく、同じ入力を1経路上で繰り返して質問しない。ここでの分岐は「どの手を指すか」ではなく、「現在盤面にこの残余完成集合があるか」である。

### 4.2 オフラインで使う勝敗関数

`k=|A_M|+|A_O|` をPからの経過着手数とする。kが偶数なら次はM、奇数ならOが指す。

`V(A_M,A_O;q)` を、入力qの下で、まだ終局していないこの状態から最善対戦したときの**Mに固定した視点の値**とする。`Q_i` を合法手iを選んだときの同じ視点での値とする。

```text
満杯で未勝利なら V=0。

Mの手番：
  i∈L(A_M∪A_O) ごとに、
  F_M(A_M∪{i})=1 なら Q_i=+1、
  それ以外なら Q_i=V(A_M∪{i}, A_O; q)。
  V=max(Q_i : i∈L(A_M∪A_O))。

Oの手番：
  i∈L(A_M∪A_O) ごとに、
  F_O(A_O∪{i})=1 なら Q_i=−1、
  それ以外なら Q_i=V(A_M, A_O∪{i}; q)。
  V=min(Q_i : i∈L(A_M∪A_O))。
```

この式中の `; q` は、最後の引数qを読みやすく分ける区切りである。未来の状態に移っても、初期盤面を表す入力qは変更しない。

生成器は、qの値を特定の盤面で固定せず、これらの条件分岐と最大・最小を関数の演算として実施する。すでに完成している状態から対局を続ける式ではない。実装が途中の状態を共有するときも、初期状態からそこへ至るまでの完成条件を先に判定するため、終局後の計算は結果に影響しない。

### 定理2　事前コンパイルされた判定図の正しさ

上式から作成し、意味を保つ節点共有と縮約を行った決定図の根は、対象形状のすべての入力qについて厳密な勝敗を返す。

**証明。** 残りマス数0の未勝利状態の値は0である。残りが少ない未終局状態で式が正しいと仮定する。Mの手番では、着手によって勝てるならその場で+1となり、それ以外の子の値は仮定により正しい。Mは最大値の手を選べる。Oの手番では、同様にOの即勝ちを−1とし、Mにとって最小の値をOが選ぶ。これで残りマス数による帰納法が成立する。帰納法とは、小さい場合の正しさから一つ大きい場合の正しさを示す証明方法である。

初期状態は `(A_M,A_O)=(∅,∅)` で未終局だから、根の関数の値は正しい。決定図の各質問は元の条件分岐と同じ意味を持つ。同じ質問と行先の共有、および `low=high` の質問の除去は、どの入力に対しても返す値を変えない。従って縮約後の根も正しい。証明終。

### 定理3　実行時評価に未来局面は不要である

判定図をあらかじめ作成しておけば、評価時はPの形状を選び、Pからqを計算し、根から1経路をたどるだけで `v(P)` を得られる。

**証明。** qの各要素は定義1のとおり現在盤面の76ラインだけで決まる。質問への答えが決まれば行先は一つに定まり、他方を調べる必要はない。石の追加、手番の更新、A_MやA_Oの生成も不要である。定理2により到達した終端の値は厳密である。証明終。

### 系1　質問回数の上限

入力変数の総数を `m` とすると、1回の評価で行う質問は高々m回である。

**証明。** 変数順序が経路上で厳密に進むため、同じ変数を2回質問しない。証明終。

本研究のE≤7の全表ではm≤32である。この32という数は、任意のゲームについての一般上限ではなく、全形状の生成済み表を調べた上限である。図全体の大きさが入力数に対して指数的に増大する場合はあり、さらに早い手数でも小容量に収まるとは限らない。

## 5. 全形状の網羅と62手目以降の直接式

### 5.1 手数だけによる適用範囲

柱の空き高さ `h_0,…,h_15` を0〜4から選び、その総和がEになる列をすべて作ることで、重力を満たす全空き形状を網羅できる。

`t` を数え上げのためだけの形式的な変数、`[t^E]f(t)` を多項式f(t)のtのE乗に掛かる係数と定義する。形状数 `N_E` は次である。

```text
N_E = [t^E](1+t+t^2+t^3+t^4)^16
```

多項式とは、変数の整数乗に係数を掛けた項を足した式である。1本の柱で0〜4個の空きを選ぶことが括弧内に対応し、16本分を掛けると、合計Eになる選び方が係数として現れる。

表の作成では、各形状で可能な残余集合の種類だけを抽出し、その存在の真偽は固定しない。従って、石の色の一部だけを選んだ標本表ではない。物理的に実現できない入力の組合せまで含むが、すべての合法配色は必ずその内側に含まれる。

|---:|---:|---:|---:|
| 0 | 65、満杯 | 1 | 0 |
| 1 | 64 | 16 | 0 |
| 2 | 63 | 136 | 1 |
| 3 | 62 | 816 | 5 |
| 4 | 61 | 3,876 | 14 |
| 5 | 60 | 15,488 | 19 |

| 7 | 58 | 168,368 | 32 |

**保証範囲は58手目以降である。** 57手目以前で定理の原理が破れるという意味ではないが、その全形状の表は今回の研究では生成していない。

### 5.2 直接式で使う追加記号

以下では局所的に空きマスをa,b,cと名付ける。どの位置を指すかは各形状で明記する。`q_M({a,c})` のような式は、a,cの空き番号を要素とする集合をq_Mへ渡す意味である。`1[条件]` は条件が真なら1、偽なら0を返す数値と定義する。

**直接式**とは、現在の残余集合の有無に対する固定された論理式であり、着手候補や子局面を実行時に列挙しない式をいう。

### 定理4　E≤3の全形状に対する直接判定

Cの下で、以下の式は厳密である。

| Eと形状σ | マスの名称 | M視点の値 |
|---|---|---|
| E=0 | なし、既勝者なし | 0 |
| E=1 | 唯一の空きマス | 0 |
| E=2、`(1,1)` | 単独マス2個 | 0 |
| E=2、`(2)` | 下a、上b | `−1[q_O({b})=1]` |
| E=3、`(1,1,1)` | 単独マスa,b,c | Mの2マス残余集合が2種類以上なら+1、それ以外0 |
| E=3、`(1,2)` | 単独a、別の柱の下b・上c | 下記の条件Jが真なら+1、それ以外0 |
| E=3、`(3)` | 同一柱を下からa,b,c | `q_O({b})=1` なら−1。そうでなく `q_M({c}) OR q_M({a,c})` が真なら+1。それ以外0 |

条件Jを次で定義する。

```text
J = q_M({c}) OR q_M({a,c})
    OR (q_M({a,b}) AND q_M({b,c}) AND NOT q_O({c}))
```

**証明。** E=1では唯一のマスが即置可能であり、Cによってそこに既存リーチはない。従って引き分け。E=2ではMとOは各1回しか指せない。別々の柱なら両マスとも初期即置可能で、双方とも完成しない。同一柱ならMが下、Oが上を取るので、上がOの既存リーチの場合だけOが勝つ。

E=3の単独3マスではMが2回、Oが1回指す。Mの2マス残余集合が2種類以上なら、3マスのうちそれらに共通するマスから指すことで二重リーチを作れる。1種類以下ならOが残りを阻止できる。Oは1回しか指せず初期即勝ちもないので、O勝ちはない。

形状 `(1,2)` でMがaを取ると、Oはb、Mはcを取る。その場合のM勝ちがJの最初の2項である。Mがbを取る場合は、Oがaを取ったときもcを取ったときもMが勝つ必要がある。最初の2項が偽のとき、この必要十分条件はJの最後の項となる。aから始めれば少なくとも引き分けなので、M負けはない。

形状 `(3)` の着手順はa,b,cに固定される。bでのOの勝利を先に判定し、それがなければcでのMの完成だけを調べればよい。以上がすべての形状である。証明終。

E=1で常に引き分けなのはCの下だけである。一般の64手目で最後のマスが白のリーチなら白勝ちになるが、それは静穏用評価より先の即勝ち処理が担当する。

## 6. 既存リーチと空き形状だけでは不足する反例

**反例**とは、ある主張が常には成り立たないことを示す具体例である。次の盤面甲・乙はいずれも60手完了、黒番、E=4である。`0x` は以後の数字が16進数であることを表す接頭辞で、表の数値は第2.3節の64ビット表現である。

| 項目 | 盤面甲 | 盤面乙 |
|---|---|---|
| `bit(B)` | `0x350ed802a969abd6` | `0x354ed802a969abd4` |
| `bit(W)` | `0xcac127cd56965429` | `0xca8127cd5696542b` |
| `bit(U)` | `0x0030003000000000` | 同じ |
| `R_M,R_O` | 両方空集合 | 両方空集合 |
| `v(P)` | −1、白勝ち | 0、引き分け |

空きマスの名前と座標は、a=(0,1,2)、b=(0,1,3)、c=(1,1,2)、d=(1,1,3)とする。この節のdは4番目の空きマスの名前である。柱は下から `(a,b)` と `(c,d)` で、a,cは段3、b,dは段4にある。

盤面甲では、黒の残余完成集合は `{b,c}`、白は `{a,c}` と `{b,d}`。盤面乙では、白の `{b,d}` だけが存在しない。

甲では、黒がどちらの柱の下を取っても、白は同じ柱の上を取る。黒には残った柱の下しかなく、最後に白が残った上を取って `{b,d}` を完成する。黒は `{b,c}` を完成できない。

乙でも白は同じ対応で黒の完成を防げる。しかし白の上2マスは四目を作らない。一方、黒の初手はaかcなので、白の唯一の完成集合 `{a,c}` は必ず阻止される。よって引き分けである。

両盤面は合法な60手の履歴を持ち、その履歴の全着手について重力・交互着手・途中に四目がないことを確認している。

### 定理5　既存リーチのみを使う一般判定の限界

`U,R_M,R_O` だけを入力とする規則は、Cを満たす61手目のすべての局面を正しく判定できない。

**証明。** 甲と乙でこの三つの入力は等しいのに、厳密値は異なるためである。証明終。

これは「現在盤面だけからの判定が不可能」という主張ではない。既存リーチに加え、残余完成集合のような情報を使う必要があることを示す。

| `evaluate_pointfir_it`, `evaluate_pointsec_it` | それぞれ先手用・後手用の、ライン状態などによる評価部分。 |
| `continuous_fir_t`, `continuous_sec_t` | それぞれ先手用・後手用の、連続するリーチに関する評価部分。 |
| `reach_layer_intersection_t` | リーチの段および両者のリーチの交差を評価する関数。turn≥60では最終盤判定を返す。 |
| `evaluate_pointfir_cont_layer_intersection_rit`, `evaluate_pointsec_cont_layer_intersection_rit` | 前述の評価部分を合成する、先手用・後手用の入口関数。 |

**PVS**はPrincipal Variation Searchの略で、最初の有望手以外を狭い探索窓で調べ、必要なら広い窓で調べ直す探索方法である。**ID**はIterative Deepeningの略で、浅い深さから深い深さへ繰り返す反復深化を意味する。これらは既存探索の名称の説明であり、新しい判定表の評価処理ではない。

### 8.2 turn≥60で実際に行われること

現行の二つの合成入口は、おおむね次の構成を持つ。

```text
合成評価 = ライン状態の評価
         + 自分の連続リーチ評価
         − 相手の連続リーチ評価
         + reach_layer_intersection_t の評価
```

turn≥60で最初の三つの寄与は0になるが、最後の関数は0へ固定されない。最後の関数内にある最終盤分岐が、勝ち・負けに対応する大きな正負の値、または引き分け相当の0を返す。

`USE_ENDGAME_R2` はその最終盤規則を切り替える**コンパイル時マクロ**、すなわちビルド時に処理を選ぶ定数名である。対象の `main_alpha_pvs_eval_inc_tbl_id_w.cpp` は、別指定がなければこれを1に設定する。ヘッダー単体に書かれた既定値0だけを見て、対象プログラムでも無効と判断してはならない。

**R2**とは旧研究の段パリティ規則で、白の段2、黒の段3、白の段4の順に有効な既存リーチを調べる規則である。段パリティとは段番号の奇数・偶数の性質をいう。旧関数は同じ柱で下に相手リーチがある候補を除く処理や、段3で双方に共有されるリーチの処理も行う。新方式はその加工済みリーチだけに依存せず、元の石集合から全残余完成集合を作る。

また、対象mainは `USE_ENDGAME_CUT` も既定で1にする。このマクロは、追加条件を満たした局面を葉に達する前に判定する既存処理を有効にする。単にEvalFnだけを書き換えても、この処理が先に値を返す場合がある。

### 8.3 静穏条件が保証される位置

現行のevaluate_boardは、自分に即勝ちがあれば先に返し、相手に即置可能リーチがあれば阻止する手に絞る。双方ともない分岐だけで通常の葉評価に進む。

新判定を呼ぶ基本位置は、**自分の即勝ちを除外し、相手の即置可能リーチもないことが分かった分岐内**である。ここではCが保証される。

`USE_ENDGAME_UNIVERSAL` は、探索型の既存無条件求解器を呼ぶ別のマクロである。その呼出し位置は静穏条件の確認より前にあるため、その名前の処理を単純に新しい静穏用表へ置き換えてはいけない。今回の方式を有効にする構成では、当該経路を無効にして、新しい呼出し位置を明示する。

## 9. 評価値の意味とスコアへの変換

### 9.1 勝敗と距離を分ける

**WDL**はWin・Draw・Loss、すなわち勝ち・引き分け・負けだけの三値結果をいう。**勝利距離**とは勝つまでの残り着手数、**最長抵抗**とは負けが避けられない側が終局をできるだけ遅らせることをいう。生成済み表はWDLだけを保存し、これらの距離を保存しない。

`INF` は現行コードの大きな評価定数で、値は1,000,000,000である。数学の無限大ではない。新しい確定WDL用のスコアの絶対値を `C_end` と定める。

```text
C_end = INF − 100000 = 999900000
score(P) = C_end × v(P)
```

`score(P)` は探索器へ返す整数評価値である。`C_end` は静穏条件Cとは別の数値である。勝ちなら999900000、負けなら−999900000、引き分けなら0を返す。この尺度は既存の段パリティ終盤評価に合わせる。

### 9.2 守るべき意味

1. 表の戻り値は**その局面の手番側視点**である。`sec` や黒白による符号反転を追加しない。
2. 新判定の後に旧評価や重みによる評価を加算しない。加算すると引き分け0や確定勝敗の尺度が変わる。
3. 自分の即勝ちは既存の `INF−turn` を優先する。Cを満たさない局面を静穏用表へ流さない。
4. 距離付き探索値とWDLスコアが同じ整数値になることは要求しない。検証ではまず三値の一致を調べる。
5. 旧モデルの非確定評価が確定スコアの帯を越えないことを確認する。越える重み設定がある場合は、尺度の扱いを先に整理する。

この計画は、**静穏な58手目以降をWDL固定値で評価する探索の仕様**を採用する。最短勝利・最長抵抗まで厳密に維持する仕様ではない。その仕様が別途必要なら、現在の表だけでは情報が足りず、追加研究が必要になる。

## 10. 判定データと実行部分の組込み

### 10.1 既存の研究用実装の定義

| 名称 | 定義 |
|---|---|
| `compiled_eval` | 研究用C++実行部分の名前空間。関連する型をまとめて名前の衝突を避ける単位。 |
| `compiled_eval::Atlas` | 全形状の索引、ライン対応、共有決定図を保持する型。Atlasは全判定表をまとめた入れ物の名前。 |
| `Atlas::evaluate(me,you)` | 手番側meと相手youの64ビット盤面を受け取り、WDLを返す関数。 |
| `me,you` | 上記関数の引数名。絶対色の黒白ではない。 |
| `atlas_e7.bin` | E≤7の生成済み判定データファイル。binはバイナリ形式、すなわち数値を直接バイト列として保存する形式を表す拡張子。 |
| `Geometry` | 一つの物理空き形状と、対応する決定図の根・各ラインの残余集合を保持するレコード。レコードは関連データを一組にしたもの。 |
| `Node` | 一つの決定図節点を保持するレコード。 |
| `empty,root,residual[j]` | Geometryの項目名。順に空きビット盤面、決定図の根番号、ファイル内のラインjに対する残余集合の整数表現。 |
| `feature,low,high` | Nodeの項目名。順に質問する入力の番号、入力0の行先、入力1の行先。 |
| `features` | 現在盤面から作った0/1を保存する、512要素の1バイト配列。 |
| `id` | 現在参照している決定図節点の識別番号。識別番号はデータを区別する整数。 |
| `p` | 入力の色番号。p=0が手番側M、p=1が相手O。 |

**配列**とは、同じ種類の値を番号順に保存する領域である。`residual[j]` の角括弧は、その配列のj番目の要素を読むことを表す。**メンバー**とは型やオブジェクトが持つ項目を指し、ドットや `::` を伴う名前は、どの型・オブジェクトに属する項目かを示す。

特徴配列の位置は `256p+s(S)` とする。256は色ごとに確保する領域の幅である。E≤7ではs(S)は0〜127に収まるが、生成形式は1バイトの集合番号を使うため幅256を取っている。

`id=0,1,2` は終端で、それぞれWDLの−1,0,+1に対応する。従って終端からの戻り値は `id−1`。**終端番号0は入力の偽を表す0とは別である。** 非終端はid≥3である。

### 10.2 評価処理の内容

```text
入力：現在の手番側の石me、相手の石you。
前提：合法、未終局、双方に即置可能リーチなし、E≤7。

1. meとyouから空きマスクを求め、対応するGeometryを選ぶ。
2. Geometry.rootが終端なら、そのWDLを返す。
3. featuresを全て0にする。
4. ファイル内の76ラインを順に読み、
   相手石がないラインの残余集合を、手番側の存在ビットとして1にする。
   手番側石がないラインの残余集合を、相手側の存在ビットとして1にする。
5. rootから始め、Node.featureが指すfeaturesが0ならlow、1ならhighへ進む。
6. 終端に達したらid−1を返す。
```

この処理には仮着手、着手後リーチの再計算、再帰呼出しがない。**再帰呼出し**とは関数が自分自身を呼んで小さい問題を解くことであり、オフライン生成や対照探索では使っても、上記評価には使わない。

研究版は静穏条件を呼出し側の契約とする。契約とは入力が満たすべき条件をいう。本番化でこの契約を曖昧にせず、初期化失敗や範囲外を0に置き換えない。

### 10.3 起動時のロードと整合検査

判定表は対局開始前に1回読み込み、両プレイヤーおよび並列の各実行単位で読み取り専用として共有する。**スレッド**とは同一プロセス内で並行して処理する実行単位であり、**読み取り専用共有**とは共通データをどのスレッドも変更しない利用法である。各評価のfeaturesは呼出しごとに別領域を使う。

将来の実装では以下を起動時に確認する。

- ファイルの識別子 `QBDD`。これは判定表形式を識別する先頭4文字で、探索を意味するQの演算子ではない。
- 対応最大空き数 `max_empty=7`、節点数、形状数、ファイル長。
- 各節点の行先と根番号が有効範囲にあり、入力番号も配列の範囲内にあること。
- 対象となる全形状を含む生成済みデータであることと、利用するデータの版。
- ファイルの数値のバイト順。今回の形式は小さい桁のバイトから格納するリトルエンディアンである。

**SHA-256**はファイル内容から256ビットの照合値を作る方法である。生成物と対応する照合値を配布時に記録し、異なる版のデータの混入を検出する。これは個々の盤面の勝敗を証明する代わりではない。

ファイルがない、壊れている、版が違う場合は、**新方式を有効とした起動を失敗させる**。評価中に表を生成する、探索で代用する、未登録を引き分けにする、といった処理は採用しない。旧方式を利用する場合は、起動時に旧方式を明示的に選んだ別設定として扱う。

**ライン順序にも注意する。** ファイルの76ラインの並びと、エンジンの `LINES` 配列の並びが同一とは限らない。研究版と同様にAtlas内のライン順序とresidualを組にして使う。既存 `BoardInc::cnt`、すなわちライン状態を保持する配列を将来再利用する場合は、先にライン集合の対応表を作って照合する。配列の同じ番号を無検査で同じラインと見なさない。

## 11. turn≥58の評価関数の作成計画

### 11.1 推奨する共通入口

新しい評価オブジェクトの名前を `EvalFnEndgame58` とする。従来評価を `legacy`、読み込み済み判定表への参照を `atlas` に保持する。legacyは「turn<58で呼ぶ従来評価」の役割名である。

```cpp
// 将来の追加例。本論文ではソースファイルを作成しない。
struct EvalFnEndgame58 {
    EvalFn legacy;
    const compiled_eval::Atlas* atlas;

    int operator()(const BoardInc& board,
                   unsigned long long rMeRaw,
                   unsigned long long rYouRaw,
                   unsigned long long hand) const {
        const int turn = board.b.turn();
        if (turn >= 58) {
            const int wdl = atlas->evaluate(board.b.Me, board.b.You);
            return (INF - 100000) * wdl;
        }
        return legacy(board, rMeRaw, rYouRaw, hand);
    }
};
```

この例の変数は、boardが現在局面、rMeRawとrYouRawが既存のrMe_rawとrYou_rawに対応する引数、handが絞込み前の即置可能マスク、wdlが表の三値結果である。atlasは起動時に正常ロードされた表を指し、関数が呼ばれる間は必ず生存する。**寿命**とはオブジェクトの作成から破棄までの期間をいう。

`struct` はデータと関数をまとめるC++の型定義、`operator()` はそのオブジェクトを関数の形で呼び出すための定義、`int` は整数型、`unsigned long long` はここで64ビット整数に用いる型である。`const` は対象をこの経路で変更しない指定、型に付く `&` は参照、`*` はポインタ、`->` はポインタが指す対象の項目参照を表す。ポインタは別のオブジェクトの場所を保持する値である。`return` は値を返して終了、`if` は条件分岐を表す。

この入口はCが保証された位置からだけ呼ぶ。検査を有効にしたビルドでは、盤面の整合、空き数、双方の即置可能リーチがないこと、atlasが有効なことを確認する。**assert**はプログラム上の前提を検査して違反時に停止する仕組みだが、実行設定で無効になるため、表のロード成功をassertだけに依存させない。

### 11.2 初期化と両プレイヤーへの設定

将来の起動処理では、研究用実行部分を本番用に分離した後、概念的に次の設定を行う。

```text
endgame_table = 起動時に読み込んだAtlasオブジェクト。
先手プレイヤーの評価 = EvalFnEndgame58(先手用の従来EvalFn, endgame_tableへの参照)。
後手プレイヤーの評価 = EvalFnEndgame58(後手用の従来EvalFn, endgame_tableへの参照)。
```

`endgame_table` は初期化例のオブジェクト名である。型別名 `AI`、すなわち長いプレイヤー型を短く呼ぶ別名は、将来 `AIPlayerPVSIncID<EvalFnEndgame58>` を使うようにする。山括弧内はC++で型を選択するテンプレート引数である。現行mainの通常対局と自己対戦用ループの両方にあるプレイヤー生成箇所を対象とする。

従来EvalFnの先手・後手モデルの選択はturn<58にだけ効く。58手目以降のWDLでは、現在局面のMeとYouをそのまま表へ渡す。先手用プレイヤーだから黒視点、後手用プレイヤーだから白視点と固定してはいけない。

### 11.3 旧処理との切替規則

新方式の有効・無効を表す将来のマクロ名を `USE_ENDGAME_TABLE58` と定める。これは**提案名であり、現行コードに存在する定義ではない**。

| 新方式有効時の項目 | 計画 |
|---|---|
| turn<58の通常葉 | 従来EvalFnへ渡す。 |
| turn≥58の静穏葉 | 新しい表評価を1回だけ実行し、固定WDLスコアを返す。 |
| `USE_ENDGAME_CUT` | 新方式の経路では旧ゲート付き打ち切りを無効化するか明示的に通さない。 |
| `USE_ENDGAME_UNIVERSAL` | 新方式の経路では無効。静穏確認前の探索型求解器に先取りさせない。 |
| `USE_ENDGAME_R2` | 旧方式用には保持できるが、新しい静穏終盤評価の後には呼ばない。 |
| 旧評価の加算 | 行わない。58、59手目で従来の非終盤成分を加えることも禁止する。 |

**58へ数字だけ変更する実装にはしない。** `evaluate_pointfir_it` など一つの関数へ新しいスコアを入れても、合成入口が他の成分を加えてしまう。上記の共通入口で、合成処理へ進む前に返す。

## 12. 葉評価の置換と58手目での打ち切り

### 12.1 段階A：既存の葉での差し替え

最初の確認段階では、通常の `level<=0` の葉評価をEvalFnEndgame58に差し替える。旧ゲート付き打ち切りが先に返さない設定にした上で、58手目以降の静穏葉で表の結果だけを返すことを検証する。

この段階は、評価関数の符号・尺度・初期化を切り分けて確認するためのもの。**levelが正の58手目では、既存探索はさらに進む。** 従って段階Aだけで「探索が必ず58手目で止まる」とは言えない。

### 12.2 段階B：静穏な58手目以降で深さに関係なく打ち切る

探索量を減らす最終的な組込み形は、新しい呼出しを `level<=0` の判定より前へ置くことである。位置は第8.3節の静穏分岐内とする。

```text
evaluate_board内の計画上の順序：

1. 既存の局面整合・終局処理、および同一評価仕様の置換表の参照。
2. 自分の即勝ちがあれば、既存の即勝ち処理で返す。
3. 相手に即置可能リーチがあれば、既存の強制応手処理へ進む。
4. 双方に即置可能リーチがない場合：
   4a. 新方式が有効でturn>=58なら、
       新評価関数を呼び、確定WDLスコアを返す。levelは問わない。
   4b. そうでなくlevel<=0なら、従来の通常葉評価を返す。
5. 残る場合は既存の探索を続ける。
```

この手順の4aは子局面を生成せず、表を呼ぶだけである。相手の即置可能リーチがある3の経路で既存探索が強制応手を扱うことは、Cを満たす葉評価の内部に探索を追加することとは異なる。今回の定理は3の局面を静穏用表で処理する保証を与えない。

全ての呼出しで満杯を引き分けとする前に、既勝者の扱いが正しいことも確認する。現行探索は勝利発生時に返して既終局盤面を子として渡さない契約を持つため、その契約を保つ。任意の外部入力を受ける検査用入口は、勝者検査を別途行う。

## 13. 置換表と探索窓との整合

### 13.1 用語と名称

| 用語・名称 | 定義 |
|---|---|
| 置換表、TT | Transposition Tableの略。同じ盤面に別の着手順で到達したとき、過去の計算結果を再利用する表。 |
| ハッシュ、`key` | 盤面から計算する照合用の値。keyはそのコード上の変数名。 |
| TTエントリ | 置換表に保存された一件のレコード。 |
| `tt.probe`、`tt.store` | 現行の置換表の検索、保存を行う操作。 |
| `depth` | エントリがどの探索深さの値を保存したかを表す項目。 |
| 探索窓、`alpha,beta` | 探索で比較対象とする下側・上側の境界。alphaが下側、betaが上側。 |
| 上界・下界 | 真の値がそれ以下であると分かる数／それ以上であると分かる数。 |
| `TT_EXACT` | 保存値が、採用した評価仕様のもとで確定値であることを表す種別。 |
| `TT_LOWER`、`TT_UPPER` | 保存値が下界だけ、上界だけであることを表す種別。 |
| `TT_NO_MOVE` | 保存すべき最善手がないことを表す既存の番兵値。番兵値は通常の手番号と区別する特別な値。 |
| `TT_STORE_LEAF` | 通常の葉評価を置換表へ保存するかを選ぶ既存のマクロ。 |
| `ev` | 以下の保存例における、新評価関数が返した整数スコア。 |

### 13.2 段階Aの保存

段階Aでは、既存の葉保存と同様に深さ0の値として扱い、WDLが厳密だからという理由だけで、距離情報を持つ深い探索の値と同一視しない。

同じ盤面でも、静穏葉の固定値と、さらに探索して得た勝利距離付きの値は整数として異なり得る。深いTTエントリの再利用を許す場合、その違いを既存の深さ付き探索仕様として明記する。新表の評価そのものの検証ではTTの先取りを無効化して比較し、表の入力が実際に通ることを確認する。

### 13.3 段階Bの保存

段階Bでは「静穏なturn≥58は、深さに関係なく固定WDLスコアを返す」という仕様に統一する。この仕様の下では、新表から得た同じ局面の値は深さや窓に依存しない。

将来の保存例は次となる。

```cpp
// 段階Bで、静穏確認後に新評価関数からevを取得した場合だけ。
tt.store(key, ev, 64, TT_EXACT, TT_NO_MOVE);
return ev;
```

ここで64は、現行の通常の要求探索深さを覆う保存深さの印として用いる案である。実装時にはエントリのdepth型と深さ比較を確認する。**「64手先まで読んだ」「勝利距離が64まで確定した」という意味ではない。** 明示的なWDL確定種別を置換表へ追加する設計にする場合は、この深さの代用よりその種別を優先して使える。

表は最善手を返さないのでTT_NO_MOVEを使い、架空の最善手を登録しない。固定WDLスコアが探索窓の外にあっても、表が求めた値そのものは確定しているため、段階Bの仕様ではTT_EXACTとしてよい。ただし親側の通常の探索による上界・下界の扱いは、既存の窓の処理に従う。

### 13.4 新旧の値を混ぜない

新旧評価方式を切り替えたとき、段階Aから段階Bへ移行したとき、判定データの版を変更したときはTTをクリアする。クリアとは過去エントリを再利用しない状態へ戻すこと。方式を切り替えながら共通TTを使う実装なら、ハッシュやエントリに評価方式を区別する情報を加える。

現在のTT参照は静穏確認より前にある。古い規則で作ったエントリが残ると、新判定へ到達する前に古い値が返るためである。新しい共通入口の追加だけではこの問題は解消しない。

本節のTT_EXACTは、第9節で定義した**固定WDLを用いる評価仕様の確定値**である。終局までの最短距離を含むゲーム値が厳密に求まった、という意味へ拡張しない。

### 14.2 実施順序

1. **評価仕様を固定する。** 第9節のWDL固定値を採用し、旧規則と距離付き値との比較基準を明記する。
2. **データを固定する。** 生成済み表を版と照合値付きで配置し、ロード・全形状対応・行先範囲を検査する。
3. **段階Aを実装する。** 共通入口と両プレイヤーの初期化を追加し、旧終盤経路を新方式から外す。
4. **段階Aを検証する。** 手番の符号、旧成分の加算がないこと、58・59手目の切替を確認する。
5. **段階Bを実装する。** 静穏分岐の深さ判定前へ呼出しを置き、同じ評価仕様でTTを保存する。
6. **対戦探索で測る。** 同じ局面・探索深さ・モデル・実行条件で、時間と調べた局面数を比較する。
7. **小さいEを軽量化する。** 必要なら第5節の直接式をC++化し、表と同じ結果であることを確認してから切り替える。未検証の高速式は導入しない。

### 14.3 正しさの受入れ条件

**受入れ条件**とは、その変更を完成と判断するために満たすべき検査項目である。

| 分類 | 必須の確認 |
|---|---|
| 境界手数 | turn=57では旧評価、58と59から新評価、60以降でも旧終盤値を加算しない。満杯の既勝者なしは0。 |
| 手番視点 | 黒番・白番の両方、先手用・後手用の両プレイヤーで、現在のMe側に対するWDLが一致する。 |
| 前提 | 自分の即勝ち、相手の即置可能リーチがある局面を静穏用表へ渡さない。 |
| 全形状 | E≤7の全空き形状に有効な根とライン対応がある。 |
| 既知の結果 | 第6節の二つの反例、保存済み600履歴、既存標本と独立探索にWDLが一致する。 |
| 呼出し経路 | 新モードで旧ゲートや探索型求解器が先に結果を返していない。 |

| 初期化 | ファイル欠落・破損・版違いを検出し、新方式の起動に失敗する。未登録を引き分けとしない。 |
| 並列実行 | 表は変更せず共有し、featuresを各呼出しで分け、対局終了まで表が生存する。 |

### 14.4 速度の受入れ条件

葉判定単体と対戦探索全体を分けて報告する。表ロード時間、常駐容量、turn別の平均時間、新判定の呼出し件数、探索節点数、1手を選ぶまでの時間を記録する。常駐容量とは対局中に保持し続けるデータ量である。

同じ標本を何度も評価する測定だけでなく、実戦の探索で次々に異なる局面を評価する場合も測る。旧方式は近似値を含むため、選んだ手や根の整数評価値が以前と同一であることを新方式の正しさの条件にしない。結果が変わった局面は独立した厳密解と照合する。

必要なコード変更と測定が終わって初めて、対戦時間の短縮を実証したと言える。本論文では、その組込みも追加測定も実施していない。

## 15. 結論

残余完成集合、柱内の空き順序、交互手番の情報を保存すると、リーチの創出を禁止せずに最善対戦の勝敗を表せる。その関数を事前に三値決定図へ変換すれば、評価時は現在盤面に対する質問だけでよく、58手目以降の全静穏局面を追加探索なしに判定できる。

対戦コードでは、既存の一部成分の `return 0` を修正するのではなく、合成評価へ入る前の共通入口を設ける。さらに静穏確認後・深さ判定前で同じ関数を呼べば、58手目以降を厳密打ち切りの境界にできる。実装時には、WDLと勝利距離を区別し、旧打ち切りの先取り、重複加算、手番の符号、TTの旧値混入を防ぐ必要がある。

本論文はこのための定義・証明・実装計画を記したものであり、既存の対戦コードには変更を加えていない。
